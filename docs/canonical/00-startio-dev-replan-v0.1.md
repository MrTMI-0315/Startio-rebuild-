# Startio 개발 재계획 V0.1

## 0. 문서 역할

이 문서는 2026년 7월 15일까지의 사업계획서, 사용자 피드백, 제품 문서, 인공지능·데이터 계약, 기존 웹·SwiftUI 코드, 모바일 V1 재설계 논의, 양대 스토어 출시 일정을 하나의 실행 기준으로 통합하고 2026년 7월 23일 시각 방향 결정을 반영한다.

이 문서가 결정하는 범위는 다음과 같다.

- 어떤 기존 코드를 유지·동결·재구축·폐기 후보로 분류할지
- iOS와 Android 동시 출시를 위해 어떤 기술 스택을 사용할지
- 사용자 경험, AI, 데이터, 안전, 개인정보, 스토어 준비를 어떤 순서로 구현할지
- 2026년 7월 19일 착수 후 어떤 일정과 증거로 다음 단계에 진입할지
- 과거 문서와 사업계획서의 어떤 항목을 유지하고 어떤 항목을 후순위 또는 가설로 분리할지

팀 공유 시 사용하는 상태와 기술 식별자는 다음 원칙으로 표기한다.

- 상태값 `LOCKED`, `DEFERRED`, `MORE`는 문서 검색과 자동화 호환성을 위해 원문을 유지하고 각각 `확정`, `출시 이후`, `추가 결정 필요`를 함께 쓴다.
- 코드·스키마·프레임워크 식별자는 원문을 유지하되 첫 등장에 한국어 의미를 덧붙인다. 예: `Task(할 일)`, `Step(단계)`, `Plan(행동 계획)`, `Proof(완료 인증)`, `History(실행 기록)`.
- P0·P1·P2, API, UI/UX, KPI, CTA, EXP처럼 팀에서 공통 식별자로 사용하는 약어는 유지하고 본문에서 한국어 의미를 설명한다.
- 파일 경로, 명령어, 열거형 값, 이벤트명, 필드명은 구현 검색과 호환성을 위해 번역하지 않는다.

문서 우선순위와 영역별 책임은 아래와 같다.

1. `AGENTS.md`: 안전, 범위, 코딩, 검증 규칙
2. 본 문서: 코드 처분, 이전 순서, 날짜, 스토어 공개 조율, 검증 운영
3. `docs/canonical/product/09-mobile-v1-reset.md`: 제품 범위, 사용자 경험, 시각, 플랫폼 계약
4. `docs/canonical/product/01-mvp-core.md`, `02-user-flow.md`, `03-feature-spec.md`: 상세 제품 동작
5. `docs/canonical/ai/04-coaching-engine.md`, `docs/canonical/data/05-behavior-event-schema.md`: AI와 데이터 계약
6. `docs/reference/research/web-p0-acceptance-matrix.md`: 기존 웹 기준선과 이전 대상 목록
7. 날짜가 있는 연구·사용자 화면·개발 문서와 사업계획서: 근거와 이력

본 문서가 사용자 경험·인공지능·이벤트 내용을 실행 관점에서 요약하더라도 해당 상세 계약을 다시 정의하지 않는다. 코드 처분·일정·출시 운영은 본 문서, 제품·사용자 경험·시각·플랫폼은 `09-mobile-v1-reset.md`, 인공지능은 `04-coaching-engine.md`와 09의 안전 결과, 이벤트·핵심 성과 지표 열거형과 산식은 `05-behavior-event-schema.md`가 우선한다.

## 1. 실행 결론

### 1.1 한 문장

> 사용자가 미루는 일을 한 줄로 적으면, 추가 설명 없이 세 개의 작은 행동으로 바꾸고 첫 행동을 바로 시작하게 하는 iOS·Android 앱을 하나의 TypeScript 코드베이스로 출시한다.

### 1.2 핵심 결정

| 질문 | 결정 |
| --- | --- |
| 기존 코드를 전부 폐기할 것인가 | 아니다. 도메인·이벤트·KPI·AI 계약·Next.js API는 재사용 후보로 유지한다. |
| 무엇을 새로 만들 것인가 | React Native + Expo 모바일 사용자 화면, 화면 이동, 저장소, 앱 수명 주기, 타이머 실행부, 동의, 스토어 설정을 새로 만든다. |
| 주 언어 | TypeScript |
| 모바일 프레임워크 | React Native + Expo 개발 빌드 |
| 제작 순서 | 화면 단위 iOS-first: 390×844 iOS 교정 뒤 같은 수직 기능 안에서 360×800 Android 동등성을 통과해야 다음 화면으로 진행. 전체 iOS 앱 선행·iOS 우선 출시는 하지 않음 |

| 출시 목표 | 2026-10-12가 포함된 공동 공개 기간, 10-19·10-26 예비 기간 |

### 1.3 일정 약속의 조건

2026년 10월 12일이 포함된 공개 목표 창은 다음 조건을 전제로 한다. 최초 Google 공개는 승인 시점 제어가 제한될 수 있으므로 10월 12일의 정확한 시각 또는 날짜를 보장하지 않는다.

- P0 외 기능을 추가하지 않는다.
- 기존 TypeScript 계약의 재사용 가능성이 스프린트 2 수직 기능 구현에서 확인된다.
- 최소 한 명의 전담 개발자와 제품·디자인 의사결정자가 확보된다.
- Apple·Google 개발자 계정과 서명 권한이 스프린트 0에 확인된다.
- 신규 Google 개인 계정이면 8월 23일까지 12명 이상의 비공개 테스터를 확보한다.
- 출시 후보 버전 이후에는 기능을 추가하지 않고 심사 차단 문제만 수정한다.

혼자 개발·기획·디자인·스토어 운영을 모두 병행하거나 계정·개인정보 결정이 지연되면 10월 26일이 포함된 예비 기간을 외부 기준으로 사용한다.

## 2. 왜 재기획하는가

### 2.1 사용자 피드백

현재 문제는 3단계 행동·타이머·인증 루프 자체보다 그 루프에 들어가기 전의 마찰이다.

- 사용자는 막힌 이유를 AI 코치에게 다시 설명하고 싶어 하지 않는다.
- 긴 대화와 카드형 대시보드는 행동 시작을 늦춘다.
- 원색·단색 위계·넓은 배경·카드 묶음으로 구성된 기존 오렌지 UI는 불편하고 낡게 느껴진다는 피드백이 있었다.
- 기록 화면은 숫자보다 실제로 시작한 흔적을 시각적으로 보여줘야 한다.
- 핵심 가치가 첫 화면과 첫 행동에서 바로 이해되어야 한다.

따라서 대화 우선 진입과 레거시 원색·단색·배경형 오렌지 사용자 화면은 모바일 V1 기본 경로에서 폐기한다. 2026-07-23 결정은 색상군 자체가 아니라 해당 표현 방식을 거부하고, 입력 우선의 근거 있는 파스텔 오렌지 방향으로 전환한다.

### 2.2 현재 저장소의 사실

- 웹: Next.js 14, React 18, TypeScript 기반 P0 흐름이 구현되어 있다.
- 재사용 후보: `lib/domain.ts`, `coaching-contract.ts`, `events.ts`, `ids.ts`, `kpi.ts`, `coaching.ts`의 순수 규칙과 검증기.
- 서버 경계: `app/api/coach/plan/route.ts`에서 AI 키를 서버에 유지할 수 있다.
- SwiftUI: iOS P0 참고 구현은 있으나 대화 우선·주황색 중심이며 Android와 공유할 수 없다.
- Android: 현재 앱 프로젝트가 없다.
- Expo/EAS: `app.json`, `app.config.*`, `eas.json`, Android 설정과 모바일 CI가 아직 없다.
- 현재 테스트는 웹 계약과 핵심 성과 지표에는 유효하지만 모바일 앱 수명 주기, 서명, 스토어 빌드를 증명하지 못한다.
- 현재 웹 안전 경로는 출시 기준선이 아니다. 서버의 `422 safety_redirect`가 웹 클라이언트에서 일반 로컬 대체 행동 계획으로 바뀔 수 있고, 로컬 대체 경로에는 임상·위험·불법 입력 분류가 완성되어 있지 않다. 형식이 정해진 안전 결과와 고정 시험 데이터 회귀 검증은 수직 기능 구현 전 P0 차단 조건이다.

### 2.3 사업계획서에서 유지할 근거

사업계획서의 다음 내용은 제품·시장 근거로 유지한다.

- 핵심 행동 흐름: 할 일 입력·장벽 분석 → 3단계 행동 분해 → 타이머 → 인증 → 경험치·레벨 → 행동 핵심 성과 지표
- 모바일 앱과 초기 가설 검증용 소개 웹페이지라는 산출물 방향
- 20~30대 만성 미루기·실행기능 어려움 사용자를 위한 비의료 실행 코칭 포지셔닝
- 고객 인터뷰 46명, PoC 16명·행동 데이터 400건 이상, 소규모 집중 파일럿 5명이라는 탐색적 검증 기록
- 시작 지연시간(Start Latency), 할 일 시작률(Task Start Rate), 완료율(Completion Rate)을 핵심 행동 지표로 본다는 판단
- 개인정보와 행동 로그를 분리하고 비식별 로그를 우선한다는 방향

다음 내용은 사업 가설 또는 후속 단계로 분리한다.

- 3일 부스터·6주 프로그램·멤버십 결제
- B2B 대학·상담센터 프로그램과 관리자 리포트
- Google Calendar 연동
- 자체 소형 언어 모델(sLLM)·7B 엔진, 폐쇄형 기관 배포, 세계 시장 확장
- 무료체험 1만 명, 유료전환 15%, 3~5억 매출, 18개월 BEP 등의 목표치
- 기관생명윤리위원회(IRB)·임상 연구 과정

`MVP 개발 완료`, `보안 아키텍처 완료`, `효능성 입증`, `행동 교정`, `실행기능 정상화`, `복제 불가 데이터 해자` 같은 표현은 코드·보안 감사·대규모 검증으로 입증되지 않았다. 제품과 스토어 문구에 사용하지 않는다. N=5/N=16 결과는 탐색적 사용자 검증이며 치료 효과로 일반화하지 않는다.

## 3. 출시 범위

### 3.1 P0 — 두 스토어에 반드시 동일하게 제공할 범위

- 한 줄 할 일 직접 입력
- 사용자가 설명하지 않아도 수행되는 내부 장벽 추론
- 정확히 세 개의 행동과 짧은 코칭 문구
- 1단계 강조와 단일 시작 핵심 실행 버튼
- 인공지능 응답 제한시간, 계약 검증, 결정론적 로컬 대체 계획, 재시도
- 1단계 → 2단계 → 3단계 순차 타이머와 앱 재진입 복구
- 필수 체크 인증, 선택적 로컬 사진 첨부, 할 일·행동 계획 기준 경험치 30을 한 번 지급
- 실행 흔적 중심 실행 기록과 기본 핵심 성과 지표
- 로컬 행동 이벤트와 핵심 성과 지표 계산. 베타 명시적 참여 동의 기반 원격 행동 데이터는 M25·M30 해소와 승인 전까지 비활성
- 안정적인 세션·할 일·행동 계획·단계 식별자 기반 행동 이벤트
- 개인정보, 인공지능 처리 설명, 의견·콘텐츠 신고, 로컬 데이터 삭제 설정
- iOS·Android 기능·이벤트 동등성
- 접근성, 앱 수명 주기, 비정상 종료, 스토어 설명 정보, 개인정보 공개, 베타 검증

### 3.2 P1 — P0 출시 이후 별도 결정

- 푸시 알림과 재진입 안내
- 자유 입력 완료 인증과 서버 사진 업로드·동기화
- 계정, 클라우드 동기화, 구독
- 주간 목표와 확장 실행 기록·보고서
- 캘린더 연동
- 최근 행동 기반 경량 개인화

P1은 각각 개인정보·스토어·동기화 비용을 포함한 별도 의사결정 기록이 있어야 한다.

### 3.3 P2 또는 명시적 비목표

- ADHD 진단·치료·선별
- 상담·의료·약물 조언 또는 위기상담 대체
- 전체 검색 증강 생성(RAG)·소형 언어 모델(sLLM)·개인화 엔진
- 기관·기업 간 거래(B2B) 대시보드와 폐쇄형 보안 배포
- 6주 프로그램 전체 운영 엔진
- 실사용자 의료·상담 원문 저장

## 4. 코드 처분과 마이그레이션

### 4.1 KEEP(유지) — 계약과 순수 로직

| 자산 | 경로 | 처리 |
| --- | --- | --- |
| P0 도메인 모델 | `lib/domain.ts` | 버전이 있는 공용 TypeScript 계약 후보로 유지 |
| 3단계·응답 검증 | `lib/coaching-contract.ts` | 정확히 3단계, 타이머, 금지 문구 검증기를 유지하고 안전 결과의 구분형 결합을 새로 보강 |
| 행동 이벤트 | `lib/events.ts` | 안정적인 식별자와 원문을 포함하지 않는 이벤트 규칙 유지 |

## 5. 모바일 V1 사용자 경험 계약

### 5.1 기본 경로

```text
앱 실행
→ 한 줄 할 일 입력
→ 최초 원격 요청 전 인공지능 처리 동의
→ 내부 장벽 추론
→ 정확히 3단계 행동 생성
→ 1단계가 펼쳐진 행동 계획 확인(2·3단계는 보이되 약하게 표시)
→ 1단계 타이머 → 2단계 타이머 → 3단계 타이머
→ 필수 체크 인증 + 선택적 로컬 사진 첨부
→ 경험치 30 한 번 지급
→ 실행 흔적·기본 핵심 성과 지표
```

### 5.2 상호작용 규칙

- 초기 안내, 계정, 장벽 선택, 감정 선택, 코치 대화를 첫 행동 계획 전에 요구하지 않는다.
- 유효한 입력 이후 기본 경로의 필수 추가 질문은 0개다.
- 입력은 앞뒤 공백 제거 후 2~240개의 유니코드 문자소 묶음만 허용한다.
- 1단계는 구체적이고 관찰 가능하며 보통 15~20초 안에 시작할 수 있어야 한다.
- 2단계와 3단계는 보이되 1단계보다 시각적으로 약하게 배치한다.
- `barrier_type`과 분류명은 P0 사용자 화면과 실행 기록에 노출하지 않는다.
- 행동 계획 편집과 단계별 타이머 직접 수정은 P0에서 제공하지 않는다.
- 화면마다 가장 눈에 띄는 핵심 실행 동작은 하나만 둔다.
- 인공지능 분석 설명은 선택형 상세 안내에 둔다.
- 원격 인공지능 실패·지연은 계약에 맞는 대체 계획으로 이어진다. 정확한 제한시간은 M21 `MORE(추가 결정 필요)`이며 해소 전 8초는 운영 확정값이 아닌 조정 가능한 작업용 보호값으로만 사용한다.
- 실행 중인 핵심 흐름에서는 비핵심 화면 이동을 숨긴다.

### 5.4 시각 시스템 — 입력 우선 파스텔 오렌지

`docs/canonical/product/10-visual-direction-2026-07-23.md`는 입력 우선 구조와 파스텔 오렌지 의미 방향을 승인한다. 정확한 HEX는 시제품·적응형 화면·접근성 검증 전까지 모두 `candidate` 또는 `provisional`이다.

| 의미 역할 | 승인 상태 | 용도 |
| --- | --- | --- |
| 배경·표면(Background·Surface) | `provisional` | 오렌지로 넓게 채우지 않는 중립 바탕과 집중 영역 |
| 기본·보조 글자(Text) | `provisional` | 읽기 위계와 보조 설명 |
| 구분선·초점(Border·Focus) | `provisional` | 영역 구분과 접근성 초점 |
| 핵심 동작(Primary Action) | 방향 승인·값 `provisional` | 따뜻하고 차분한 파스텔 오렌지, 화면당 하나 |
| 상호작용 상태(Pressed·Disabled·Selected) | `provisional` | 동작 상태를 색상 외 단서와 함께 표현 |
| 완료·주의·파괴(Success·Caution·Destructive) | `provisional` | 상태 간 의미 구분 |

규칙:

- 원색 오렌지, 단일 오렌지 위계, 넓은 오렌지 페이지 바탕·그라디언트, 레거시 오렌지 카드·대시보드를 사용하지 않는다.
- 코발트와 Willbyte Blue를 제품 Primary의 기본값이나 암묵적 별칭으로 사용하지 않는다.
- 큰 둥근 카드 묶음과 강한 그림자 대신 여백, 글자 체계, 1픽셀 구분선을 우선한다.
- 390×844 iOS와 360×800 Android에서 첫 화면 입력란·핵심 실행 버튼을 스크롤 없이 사용할 수 있어야 한다.
- 첫 화면은 즉시 작성 가능한 입력란과 `첫 행동 만들기`만 강한 행동 위계로 두고 입력예시·결과 약속·기능 설명을 중첩하지 않는다.
- WCAG 2.2 AA, iOS 44포인트·Android 48dp 터치 영역, 동적 글자 크기, VoiceOver·TalkBack을 지원한다.
- 상태를 색상만으로 표현하지 않는다.
- 디자인 토큰 확정 전에 Light·Dark·Increased Contrast 및 상태별 검증과 대표 사용자 5명 중 최소 4명의 3초 입력 인지·CTA 의미 검증을 통과한다.

## 6. 인공지능·안전·대체 계획 계약

### 6.1 AI의 역할

AI는 자유 대화형 상담사가 아니라 정해진 규칙 안에서 작은 행동을 만드는 비임상 실행 코치다.

- 내부에서 할 일, 감정, 상황, 실행 장벽 유형(`barrier_type`)을 추론한다.
- 사용자에게 실행 장벽이나 감정 설명을 요구하지 않는다.
- 정확히 3단계, 타이머, 완료 조건, 짧은 코치 문구를 반환한다.
- P0에서는 정적 규칙, 지시문 양식, 구조화 출력, 대체 계획으로 충분하다.
- 전체 검색 증강 생성(RAG)·소형 언어 모델(sLLM)은 구현하지 않는다.

### 6.2 결과 종류

```text
plan_allowed
- 정확히 3개의 계약에 맞는 행동
- do_not_chunk: false

safe_redirect
- reason_code: clinical_advice_request | crisis_or_self_harm | dangerous_or_illegal_request
- 짧은 경계/지원 안내
- do_not_chunk: true
- plan 없음
```

`safe_redirect`는 타이머, 완료 인증, 경험치, 실행 장벽 추론, 원문 행동 이벤트를 만들지 않는다. 안전한 입력에 인공지능 제공자가 진단적·공격적·계약 위반 출력을 주면 해당 출력을 폐기하고 로컬 `plan_allowed` 대체 계획과 신고 동작을 제공한다.

이 결과 결합은 현재 코드에 완전하게 구현된 계약이 아니라 모바일 V1 선행 구현 과제다. 서버와 클라이언트는 안전하지 않은 결과를 HTTP 오류와 일반 대체 계획으로 뭉개지 않고 같은 형식의 결과로 처리해야 한다. 임상, 위기·자해, 위험·불법 고정 시험 데이터마다 행동 계획·타이머·완료 인증·경험치·이벤트가 생성되지 않는 회귀 검증을 먼저 고정한다.

### 6.3 금지 주장

- ADHD가 있다고 단정
- ADHD 또는 임상 증상을 치료·개선한다고 주장
- 상담·치료·약물을 대체하거나 조정하라고 안내
- 사용자에게 의지 부족이나 실패 책임을 귀속
- 탐색적 사용자 테스트를 임상 효능으로 표현

## 7. 데이터, 개인정보, 보안 계약

### 7.1 데이터 원칙

- 행동 이벤트에는 원문 할 일, 이메일, 진단, 상담 기록, 약물, 의료 문서를 저장하지 않는다.
- 행동 계획 요청에는 원문 할 일이 필요할 수 있지만 행동 분석과 분리한다.
- 로컬 이벤트는 실행 기록·핵심 성과 지표의 기준 원천이다.
- 원격 행동 데이터는 베타 참여자가 인공지능 처리 동의와 분리된 버전별 명시적 참여 동의를 한 경우에만 허용 목록 투영값을 전송하며, 일반 공개 기본값은 비활성이다.
- M25·M30 해소 후 원격 행동 데이터가 승인될 경우에만 허용 목록을 `install_scoped_id`, 앱 버전, 플랫폼, 이벤트명·시각, 세션·할 일·행동 계획·단계 식별자, 단계 번호, 지속시간, 완료 상태, 대체 계획·오류 코드로 제한한다.
- 원격 이벤트에는 원문 할 일, 생성 행동·코치 문구, 사진·경로, 이메일, 의료·진단 정보, 자유 입력 의견을 보내지 않는다.
- 승인된 원격 행동 데이터 전송이 없는 로컬 전용 V1은 `install_scoped_id`를 만들지 않는다. M25·M30 승인 시에만 최초 실행에서 무작위 앱 범위 식별자를 만들고 광고 식별자·이메일·기기 계정과 연결하지 않으며 최대 원격 보관 기간은 90일로 제한한다.
- 전송 실패 대기열과 재시도는 크기·횟수를 제한하고, 설치 식별자 기반 원격 삭제 경로를 제공한다.
- 로컬 삭제는 할 일, 완료 인증, 실행 기록, 경험치, 설치 식별자, 동의, 대기열을 함께 지운다.
- 콘텐츠 신고는 원격 행동 데이터와 분리하고 사용자가 전송 내용을 미리 확인한다.

### 7.2 유지할 이벤트·핵심 성과 지표

대표 이벤트 흐름은 아래와 같다. 정확한 열거형, 별칭, 필수 필드는 `docs/canonical/data/05-behavior-event-schema.md`만을 기준 문서로 사용한다.

```text
app_opened, session_started, session_resumed, session_ended, session_abandoned
task_created/task_submitted
barrier_analyzed/barrier_detected
action_plan_generated/plan_generated
timer_started, timer_paused, timer_completed, timer_abandoned
proof_submitted, exp_granted
task_restarted, reentry_prompt_created
fallback_used, remote_timeout, api_error
```

핵심 식별자:

```text
session_id, task_id, plan_id, step_id, step_index, assigned_step_count
```

P0 핵심 성과 지표:

- 시작 지연시간(Start Latency)
- 할 일 시작률(Task Start Rate)
- 할 일 단위 완료율
- 단계 단위 완료율
- 이탈 지점
- 복귀율
- 누적 경험치와 최근 실행 흔적

각 단계는 별도 타이머 이벤트 흐름을 가진다. 완료 인증은 3단계 완료 뒤 최종 할 일 단계에서 한 번 제출하며 경험치는 `task_id + plan_id` 기준으로 30을 한 번만 지급한다.

### 7.3 이미지와 계정

- 체크 인증은 P0 필수이고 로컬 사진 첨부는 P0 선택 기능이다. 사진 없이도 완료와 경험치 지급이 가능하다.
- 사진은 앱 소유 로컬 저장소에만 보관하고 서버, 원격 행동 데이터, 콘텐츠 신고로 업로드하지 않는다. 경로 역시 행동 분석에 기록하지 않는다.
- 실행 기록은 사용자가 첨부한 경우에만 작은 로컬 미리보기 이미지를 표시하며 전체 데이터 삭제는 원본·미리보기·기록을 함께 지운다.
- 사진 권한은 사용자가 첨부를 선택하는 시점에만 요청한다. 운영체제 백업을 포함한 보관 동작은 Expo 기준선에서 검증한다.
- 계정·결제·클라우드 동기화도 P0에서 제외한다.
- 계정을 추가하는 출시는 Apple·Google 계정 삭제 요건과 서버 삭제를 함께 구현한다.

### 7.4 공개 API 보강

출시 전 행동 계획 API에 다음을 추가하거나 검증한다.

- 요청 크기 제한
- 호출 빈도·악용 제한
- 강제 응답 제한시간과 요청 취소
- 스키마 검증과 안전 결과 결합
- 원문 입력 없는 구조화 관측 정보
- 인공지능 키 서버 보관
- M25·M30 승인 뒤에만 허용 목록 이벤트·삭제 통신 경로를 추가한다. 콘텐츠 신고 통신 경로는 M33 정책 확인 뒤 별도 경계로 결정하며 운영 URL과 운영 담당자는 `MORE(추가 결정 필요)`를 해소한 뒤 설정한다.

```text

  Expo 앱, 화면 이동, 사용자 화면, AppState, 저장소 어댑터, 설정

packages/domain/
  행동 계획, 타이머, 완료 인증, 경험치, 핵심 성과 지표 계약과 순수 로직

packages/events/
  이벤트 스키마·이름, 안정적인 식별자 도우미, 개인정보 투영

app/api/coach/plan/
  기존 Next.js 서버 행동 계획 경계

ios/StartioNative/
  모바일 V1 인수 기준 통과 전까지 기능 동등성·앱 수명 주기 참고 자료
```

저장소는 기존 npm 패키지 관리자를 유지하고 루트 npm 작업공간 아래 `apps/mobile`과 기존 Next.js 앱을 함께 둔다. 스프린트 0에는 패키지 내보내기·빌드, 공용 TypeScript 설정, Next `transpilePackages`, Metro 해석기·감시, 루트·모바일 설치와 지속적 통합 명령, 서버 전용 모듈이 Metro 묶음에 들어가지 않는 보호 규칙을 검증한다. 대규모 선행 패키지 이동은 하지 않는다.

초기부터 대규모 단일 저장소 재구성을 하지 않는다. 다음 순서로 이동한다.

1. 현재 순수 로직, 부수 효과, API 계약, 저장 형식을 목록화한다.
2. 광범위한 패키지 추출 없이 얇은 `plan_allowed | safe_redirect` 호환 경계와 안전하지 않은 입력의 고정 시험 데이터 회귀 검증을 먼저 고정한다.
3. 저장소 구조를 크게 바꾸지 않고 Expo API 연결 수직 기능을 만든다. 각 화면은 390×844 iOS 설계·구현을 먼저 교정하고, 같은 수직 기능 안에서 360×800 Android 동등성을 통과한 뒤 다음 화면으로 진행한다.
4. 수직 기능 구현에서 재사용이 증명된 순수 TypeScript만 패키지로 추출한다.
5. 모바일 저장소, 앱 수명 주기, 타이머, 접근성, 동의와 전체 P0 시험 가능 빌드를 구현한다.
6. API 경계를 강화하고 원격 행동 데이터·신고 경계는 M25·M30·M33 해소 결과에 따라 추가한다.
7. 전체 P0, 베타, 개인정보, 스토어 통과 기준을 충족한다.

모바일 프로세스 종료 콜백은 신뢰 가능한 앱 수명 주기 이벤트가 아니다. 타이머와 세션은 종료 콜백을 전제로 하지 않고 매 상태 전이의 시각 기록을 저장한 뒤 다음 최초 실행에서 상태를 재계산한다.

수직 기능 구현과 한 번의 제한된 보완 스프린트 후에도 양 플랫폼의 앱 수명 주기 정확성, 입력 준비성, 행동 계획부터 타이머까지의 성능을 맞추지 못하면 React Native·Expo 결정을 재검토한다. 그 전에는 공용 패키지 추출을 확대하지 않는다.

### 10.2 수직 기능 구현 통과 기준

- 실제 iOS와 Android에서 입력 → 행동 계획 → 타이머가 동작한다.
- 유효한 입력 뒤 필수 추가 질문은 0개다.
- 할 일 입력란이 상호작용 가능한 상태까지 1.5초 이하를 목표로 한다.
- 성공한 행동 계획 응답시간의 중앙값은 3초 이하를 목표로 한다. 95백분위·제한시간 8초는 M21 해소 전 임시 측정 목표다.
- 모든 모의 인공지능 제공자 실패가 진행 불가 상태 없는 사용 가능한 대체 계획으로 이어져야 하며 앱 전체 제한시간은 M21에서 확정한다.
- 원문 입력이 행동 분석에 포함되지 않는다.
- 임상·위기·위험 고정 시험 데이터가 행동 계획, 타이머, 완료 인증, 경험치, 행동 이벤트를 만들지 않는다.

### 10.3 비공개 테스트 진입 기준 — 8월 23일

- 입력 → 행동 계획·대체 계획 → 3단계 타이머 → 완료 인증·경험치 → 실행 기록의 전체 P0 시험 가능 빌드가 양 플랫폼에 있다.

- 전체 P0 자동 시험 행렬이 통과한다.
- 백그라운드·포그라운드·프로세스 종료·재실행 타이머와 멱등성이 실기기에서 통과한다.
- VoiceOver·TalkBack, 큰 글자, 한국어 환경, 최소·현재 운영체제 시험 행렬에 P0 차단 문제가 없다.
- TestFlight 외부 베타와 필요한 Play 비공개 시험 참여 집단이 활성화된다.
- 개인정보 공개 초안이 실제 소프트웨어 개발 도구·네트워크 전송 내용과 일치한다.
- 적용 계정은 12명·14일 충족과 운영 공개 권한 상태를 확인한다. 미충족이면 목표 공개 기간을 예비 기간으로 전환한다.

### 10.5 출시 후보 통과 기준

- 동일 후보 빌드에서 도메인, API, 모바일 전체 구간, 빌드, 개인정보 검사를 두 번 연속 통과한다.
- 출시 차단 및 심각도 1·심각도 2 결함은 0개다.
- 허용된 낮은 심각도 결함은 담당자, 영향, 예외 승인, 후속 확인일이 있다.
- 스토어 설명 정보, 고객지원 URL, 개인정보 URL, 콘텐츠 신고, 로컬 삭제가 동작한다.
- Apple 개인정보 명세와 제3자 소프트웨어 개발 도구 선언, 현재 Apple 제출용 개발 도구, Google 목표 API, 앱 개인정보·데이터 안전, Google 인공지능 생성 콘텐츠 신고 정책을 실제 빌드·네트워크 동작과 대조한다.
- 감시, 고객지원, 되돌리기, 데이터 사고 담당자가 운영 절차서를 승인한다.

### 10.6 최초 운영 공개 통과 기준

- Apple 후보 빌드가 승인되어 수동 공개 보류 상태다.
- Google 운영 공개 권한이 승인되고 운영 후보 빌드가 내부 출시 통과 기준을 충족했다.
- 서명된 `release_window_sla`, 고객지원·감시, 되돌리기, 사고 담당자가 준비됐다.
- 이 기준을 통과한 뒤 첫 Google 운영 버전을 제출하고 Google 공개 확인 즉시 iOS 수동 공개를 실행한다.

## 11. Beta 학습 지표

최소 20명의 대표 참여자를 모집하며 그중 최소 5명은 시제품 단계에 포함한다.

- 앱 실행 → 할 일 제출
- 할 일 제출 → 행동 계획 표시
- 행동 계획 표시 → 첫 타이머 시작
- 타이머 시작 → 완료·포기
- 필수 추가 질문 수
- 대체 계획 진입과 성공
- 플랫폼·앱 버전·참여 집단

출시 판단 기준값:

- 대화 우선 iOS 기준선 대비 앱 실행 → 타이머 시작 중앙값 40% 이상 감소
- 5분 내 유효한 할 일 제출 → 첫 타이머 시작 전환율 15%포인트 이상 개선
- 행동 계획 수락 전 이탈 30% 이상 감소
- 최소 90%가 진행자의 도움 없이 타이머 시작

과거 기준선을 신뢰할 수 없으면 개선율을 꾸며내지 않고 진행자 동반 비교 연구로 대체한다. 충족하지 못한 기준값은 사용자 경험 재실험 또는 증거 공백·담당자·후속 확인일이 기록된 제품 위험 예외 승인이 필요하다. 이 수치는 치료 효과가 아니라 제품 사용성 지표다.

## 14. Sprint 0 결정 등록부

2026년 7월 15일 모바일 V1 결정 회의부터 상태는 아래 세 값만 사용한다.

- `LOCKED(확정)`: 회의에서 방향이 명시적으로 합의되었거나 안전·개인정보상 변경할 수 없는 최소 계약
- `DEFERRED(출시 이후)`: 모바일 V1에서 제외하고 후속 출시 의사결정으로 넘긴 항목
- `MORE(추가 결정 필요)`: 결론이 없거나, 용어·정책·기술·실제 계정 값에 대한 추가 확인이 필요한 항목

`MORE(추가 결정 필요)`는 임의 구현을 허용한다는 뜻이 아니다. 해소 전에는 범위를 늘리지 않는 최소 구현을 사용한다. 안전·개인정보·스토어 요구가 걸린 항목은 보수적인 현행 기준을 유지하고, 실제 값과 담당자가 확인되기 전 운영 환경 값을 추정하지 않는다.

첨부안의 새 실행 장벽 이름은 기존 코드·스키마와 동의어가 많아 채택하지 않았다. 새 할 일 범주는 모바일 V1 목표 계약으로 확정한다. 과거 분석 행은 원문으로 재추론하지 않고 `study→studying`, 의미가 넓은 `work/home/personal→general`로 버전이 있는 이전을 수행한다. 새 원격 응답의 잘못된 범주는 이 이전표로 강제 변환하지 않고 응답 전체를 폐기한다. 특정 저장소·사진 패키지와 최소 운영체제 버전은 실제 Expo 기준선·실기기 검증 전에는 임의로 고정하지 않는다.

## 16. 완료 정의

모바일 V1은 다음이 모두 참일 때만 완료다.

- iOS와 Android에서 동일한 P0 계약과 이벤트 의미가 동작한다.
- 직접 입력부터 완료 인증·경험치·실행 기록까지 전체 흐름이 실기기에서 통과한다.
- 1·2·3단계 타이머가 순차 완료되고 재실행 시 현재 단계로 복구된다.
- 체크만으로 완료할 수 있고 선택 사진은 로컬에서만 표시·삭제된다.
- 필수 코칭 대화가 없다.
- M21에서 확정된 응답 제한시간과 모든 인공지능 제공자 실패가 진행 불가 상태 없는 대체 계획으로 이어진다. 해소 전 8초는 임시 시험 보호값이다.
- 타이머가 백그라운드, 프로세스 종료, 재실행 후 정확히 복구된다.
- 완료 인증·경험치·이벤트가 중복 동작에도 중복 생성되지 않는다.
- 원문 할 일, 의료·상담 원문, 인공지능 제공자 전송 내용이 행동 분석·내보내기에 없다.
- 원격 전송 내용에서 생성 문구, 사진, 사진 경로, 이메일, 의료·자유 입력 데이터가 0건이다.
- 안전 고정 시험 데이터가 `plan_allowed | safe_redirect` 계약을 통과한다.
- 성능, 개인정보, 로컬 삭제 통과 기준을 충족하고 접근성과 콘텐츠 신고는 M34·M33 해소 결과로 확정된 출시 통과 기준을 충족한다.
- P1/P2가 P0에 포함되지 않는다.
- iOS가 승인되어 수동 공개 보류되고 Google 후보 빌드가 내부 출시 통과 기준을 충족한 뒤 첫 운영 버전을 제출하며, Google 공개 확인 후 서명된 허용시간 안에 iOS가 공개된다.
- 출시 감시, 고객지원, 되돌리기, 데이터 사고 담당자가 정해진다.

## 17. 다음 즉시 작업

1. 우선순위 `MORE(추가 결정 필요)` 결정의 실제 담당자·값·해소 증거를 채우고 `LOCKED(확정)` 결정만 야간 작업 묶음으로 실행한다.
2. Apple·Google 계정 상태와 Google 12명·14일 적용 여부를 7월 21일까지 확인한다.
3. 사용자 5명용 클릭 가능한 시제품과 비교 질문지를 준비한다.
4. Expo 개발 빌드용 최소 뼈대와 양 플랫폼 실기기 환경을 준비한다.
5. 현재 깨진 웹 안전 경로를 기준선으로 사용하지 않는다. `plan_allowed | safe_redirect` 형식 계약과 안전하지 않은 입력에서 행동 계획이 생성되지 않는 고정 시험 데이터를 먼저 구현·테스트한 뒤 이벤트, 식별자, 핵심 성과 지표 추출 경계를 고정한다.
6. 8월 23일 비공개 베타를 위해 실제 목표 사용자 12~15명의 시험 사용자 집단을 모집한다.
