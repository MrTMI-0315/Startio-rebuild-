# Startio 모바일 V1 제품·개발 재설계

## 1. 결정 요약

Startio 모바일 V1은 iOS와 Android에서 하나의 React Native + Expo 앱으로 개발해 공동 공개 기간에 출시한다. 목표는 2026년 10월 12일이 포함된 주간이며, 10월 19일과 10월 26일이 포함된 주간을 예비 기간으로 둔다. 같은 달력 날짜 안의 공동 공개와 최대 48시간 허용은 제품 담당자가 정확한 `release_window_sla`에 서명할 때까지 작업 가정이다. 기본 경험은 코칭 대화가 아니다. 사용자가 미루는 일 하나를 입력하면 Startio가 내부에서 실행 장벽을 추론하고 정확히 세 개의 작은 행동을 반환하며 시작 버튼 하나와 함께 첫 행동을 보여준다.

제품 약속:

> 미루는 일을 한 줄로 적으면, 추가 설명 없이 3개의 작은 행동으로 바꿔 첫 행동을 바로 시작하게 한다.

짧은 문구:

> 할 일을 적으세요. 첫 행동은 Startio가 만듭니다.

첫 상용 출시는 P0 핵심 흐름에 집중한다. 체크 인증과 선택적 로컬 전용 최종 사진 첨부는 포함한다. 서버 사진 업로드·동기화, 캘린더 연동, 전체 개인화, 소형 언어 모델(sLLM), 기관 기능, 임상 주장은 포함하지 않는다.

### 1.1 2026-07-15 결정 회의 반영

`docs/canonical/00-startio-dev-replan-v0.1.md` 14절이 2026년 7월 15일 모바일 V1 회의의 결정 상태 기준이다. 이 문서는 보수적인 구현 기준선을 계속 제공하지만 `MORE(추가 결정 필요)` 항목은 사용자가 승인한 제품 확정안이 아니며 범위를 확장하는 근거로 사용할 수 없다.

- 직접 입력, 행동 계획 → 타이머 → 완료 인증 → 경험치 → 실행 기록 흐름, 단계별 순차 타이머, 체크 인증, 선택적 로컬 사진, 할 일 단위 경험치 한 번 지급, 짧은 도움말형 문구, 레거시 원색·단색·배경형 오렌지 화면 제거, 단일 핵심 실행 버튼은 `LOCKED(확정)`이다.
- 행동 계획·타이머 편집, 대화 우선 코칭, 확장 이벤트·핵심 성과 지표, 푸시, 계정·동기화, 결제, 캘린더, 서버 사진, 고도화 개인화·검색 증강 생성(RAG)·소형 언어 모델(sLLM)은 `DEFERRED(출시 이후)`다.
- 모호한 입력의 추가 질문 규칙, 백그라운드·재실행 경과시간, 포기·재시작 상태 전이, 실행 기록·핵심 성과 지표 표시, 실행 장벽 결과 표시, 정확한 응답 제한시간, `safe_redirect` 표시, 원격 행동 데이터·설치 식별자, 콘텐츠 신고 정책 적용, 접근성 수준, 파스텔 오렌지 방향 안의 정확한 색상값, 시각 정보 밀도·동등성 기준, 스토어 식별정보, 출시일은 `MORE(추가 결정 필요)`다.

### 1.2 2026-07-23 시각 방향 결정

`docs/canonical/product/10-visual-direction-2026-07-23.md`는 코발트 Primary·오렌지 Warning-only 규칙을 대체한다. 입력 우선의 파스텔 오렌지 방향과 `첫 행동 만들기` 단일 CTA는 승인됐으며, 정확한 HEX 토큰은 Light·Dark·Increased Contrast·상태별 WCAG 2.2 AA와 5인 첫인상 시험 전까지 `provisional`이다. 이 변경은 기능·안전·개인정보·플랫폼 의미 계약을 변경하지 않는다.

`MORE(추가 결정 필요)` 항목이 해소될 때까지 가장 범위가 작은 안전 기본값을 사용한다. 필수 추가 질문 0개, 실행 장벽 이름 미표시, 원격 행동 데이터 전송 비활성, 설치 범위 원격 식별자 미생성, 원문·생성 문구·사진 전송 금지, 운영·스토어 값 추정 금지를 적용한다. 행동 계획을 만들지 않는 안전 동작과 스토어가 의무화한 신고·접근성 요건은 정확한 사용자 화면이 미정이어도 출시 보호 규칙으로 유지한다.

## 2. 재설계 이유

세 가지 근거가 같은 수정 방향을 가리킨다.

| 근거 | 확인 내용 | 제품 결정 |
| --- | --- | --- |
| 사용자 피드백 | 일이 막힌 이유를 설명하는 것 자체가 추가 작업으로 느껴짐 | 실행 장벽 분류를 내부 인공지능 동작으로 전환 |
| 사용자 피드백 | 대화가 느리고 글과 카드가 너무 많음 | 정상 경로에서 코칭 질문 0개, 화면마다 핵심 실행 동작 1개 |
| 사용자 피드백 | 원색·단색 위계·넓은 배경·카드 묶음으로 구성된 기존 오렌지 화면이 낡거나 불편하게 느껴짐 | 레거시 표현은 제거하고 중립 표면과 근거 있는 파스텔 오렌지 Primary Action을 사용 |
| 현재 웹 점검 | 직접 입력 P0 흐름, 이벤트 모델, 핵심 성과 지표 로직은 재사용 후보지만 안전·대체 계획 경계는 출시 안전성을 충족하지 못함 | 검증된 도메인 계약은 유지하고 형식이 정해진 안전 경계를 먼저 수정한 뒤 모바일 표현과 앱 수명 주기 처리를 교체 |
| 현재 iOS 점검 | SwiftUI 시제품은 대화 우선이고 Android 클라이언트가 없음 | 서로 다른 두 클라이언트를 확장하지 않고 하나의 양 플랫폼 모바일 클라이언트 개발 |
| 2026 사업계획서 | 모바일 상용 출시와 시험 사용자 모집이 예정됨 | 제품 일정에 스토어, 개인정보, 베타, 출시 준비 통과 기준 추가 |

사업계획서는 사업 맥락으로 유지한다. 그 문서의 대화형 접수, 캘린더, 소형 언어 모델, 기업 기능, 연구 단계 약속은 P0 구현 경계를 덮어쓰지 않는다.

## 3. 모바일 V1 경험 계약

### 3.1 첫 사용 정상 경로

1. 앱은 할 일 입력란에 초점이 맞고 키보드를 사용할 수 있는 상태로 열린다.
2. 사용자가 할 일 하나를 입력하고 `첫 행동 만들기`를 누른다.
3. 최초 원격 제출에만 Startio가 짧고 명시적인 인공지능 처리 동의를 요청한다. 제공자 범주와 목적을 밝히며 거절하면 로컬 대체 계획으로 계속 진행한다.
4. Startio는 사용자에게 실행 장벽이나 감정 이름을 묻지 않고 행동 계획을 생성한다.
5. 결과는 1단계를 강조하고 2·3단계는 접거나 시각적으로 약하게 보여준다.
6. 사용자가 `지금 시작` 버튼 하나를 누른다.
7. 1·2·3단계가 각각 시각 기록 기반 순차 타이머로 실행된다.
8. 현재 단계는 완료·일시정지·포기할 수 있다. 프로세스 재실행 시 현재 단계와 이어하기 동작을 복구한다. 정확한 상태 전이는 `MORE(추가 결정 필요)`다.
9. 3단계 뒤 체크 인증이 있어야 완료된다. 로컬 사진 하나를 추가할 수 있지만 사진은 필수가 아니다.
10. 최종 인증은 할 일·행동 계획마다 경험치 30을 한 번 지급하고, 대화를 다시 열지 않은 채 실행 흔적과 핵심 성과 지표 이벤트를 기록한다.

대화가 0개라는 뜻이 타이머 자동 시작을 의미하지는 않는다. 시작 버튼 한 번은 사용자의 결정권을 보존하고 예상하지 못한 카운트다운을 막는다.

### 3.2 상호작용 규칙

- 첫 행동 계획 전에 초기 안내, 계정 생성, 실행 장벽 선택, 감정 선택, 코칭 대화를 요구하지 않는다. 인공지능 처리 동의는 초기 안내 절차가 아니라 필요한 시점의 개인정보 통제다.
- 정상 경로에서 유효한 할 일 입력 뒤 추가 질문을 요구하지 않는다.
- 앞뒤 공백 제거 후 2~240개의 유니코드 문자소 묶음을 허용한다. 그 외 입력은 네트워크 요청 없이 화면 안의 짧은 문구 하나로 수정하도록 안내한다.
- 정확히 세 개의 행동을 사용한다. 1단계는 구체적이고 관찰 가능하며 보통 15~20초 안에 시작할 수 있어야 한다.
- 화면마다 가장 눈에 띄는 핵심 실행 동작을 하나만 보여준다.
- 행동 계획 문구는 짧게 유지한다. P0 사용자 화면과 실행 기록에 `barrier_type` 또는 사용자 유형 이름을 노출하지 않는다. 선택형 상세 안내는 분류명을 쓰지 않고 행동을 작게 만든 이유를 설명할 수 있다.
- P0에서 행동 계획 또는 단계별 타이머 편집을 허용하지 않는다.
- 허용된 할 일의 원격 행동 계획이 느리거나, 사용할 수 없거나, 잘못되거나, 동의를 거절한 경우 결정론적 로컬 대체 계획을 제공한다. 안전하지 않은 입력은 대체 행동 계획이 아니라 `safe_redirect`를 반환한다.
- 핵심 흐름을 실행하는 동안 비핵심 화면 이동을 숨긴다. 흐름 밖의 최상위 화면은 시작, 실행 기록, 설정으로 제한한다.

### 3.3 안전 결과 계약

모바일 V1 행동 계획은 두 가지 명시적 결과 중 하나를 반환한다.

```text
plan_allowed
- plan: 계약에 맞는 정확히 세 개의 행동
- do_not_chunk: false

safe_redirect
- reason_code: clinical_advice_request | crisis_or_self_harm | dangerous_or_illegal_request
- message: 짧은 비임상 경계 안내 또는 긴급 지원 안내
- support_actions: 안전한 행동 또는 지원 경로 1~3개
- do_not_chunk: true
- plan: 없음
```

필수 고정 시험 데이터:

- 진료 예약 같은 실용적 할 일을 포함한 일반적인 안전 입력은 `plan_allowed`를 반환한다.
- 진단, 치료, 약물 조정, 상담 대체 요청은 `safe_redirect/clinical_advice_request`를 반환한다.
- 위기 또는 자해 의도는 `safe_redirect/crisis_or_self_harm`을 반환하고 지역 긴급·위기 지원 경로를 우선한다.
- 위험하거나 불법인 행동 요청은 `safe_redirect/dangerous_or_illegal_request`를 반환한다.
- 안전한 입력에 인공지능 제공자가 공격적·진단적·계약 위반 출력을 주면 해당 출력을 폐기하고 계약에 맞는 로컬 `plan_allowed` 대체 계획과 콘텐츠 신고 동작을 제공한다.

`safe_redirect` 결과는 타이머, 완료 인증, 경험치, 실행 장벽 추론, 원문이 포함된 행동 전송 내용을 만들지 않는다. 이 계약은 Startio를 위기상담 서비스로 만들지 않으면서 `docs/reference/research/safety-copy-boundary.md`의 언어 경계를 실행 규칙으로 만든다.

### 3.4 시각 방향: 입력 우선 파스텔 오렌지

시각 체계는 동기 부여형·게임형보다 차분하고 정밀하며 현대적으로 느껴져야 한다. `docs/canonical/product/10-visual-direction-2026-07-23.md`의 파스텔 오렌지 방향은 승인됐지만 정확한 색상값은 아직 승인되지 않았다.

| 의미 역할 | 승인 상태 | 용도 |
| --- | --- | --- |
| 배경(Background) | `provisional` | 오렌지로 넓게 채우지 않는 중립 앱 바탕 |
| 표면(Surface) | `provisional` | 입력과 집중 콘텐츠 영역 |
| 기본·보조 글자(Text) | `provisional` | 읽기 위계와 보조 설명 |
| 구분선·초점(Border·Focus) | `provisional` | 영역 구분과 키보드·접근성 초점 |
| 핵심 동작(Primary Action) | 방향 승인·값 `provisional` | 따뜻하고 차분한 파스텔 오렌지, 화면당 하나 |
| 눌림·비활성·선택(Interaction States) | `provisional` | 동작 상태를 색상 외 단서와 함께 표현 |
| 완료(Success) | `provisional` | 완료 상태 |
| 주의·파괴(Caution·Destructive) | `provisional` | 주의와 위험 상태를 서로 구분 |

규칙:

- 원색 오렌지, 단일 오렌지 위계, 넓은 오렌지 페이지 바탕·그라디언트, 레거시 오렌지 카드·대시보드를 사용하지 않는다.
- 코발트와 Willbyte Blue를 제품 Primary의 기본값이나 암묵적 별칭으로 사용하지 않는다.
- 큰 둥근 카드 묶음과 강한 그림자보다 여백, 글자 체계, 1픽셀 테두리를 우선한다.
- 첫 화면은 즉시 작성 가능한 입력란이 가장 강한 상호작용이고 `첫 행동 만들기`가 유일한 주요 CTA다.
- 입력예시·결과 약속·기능 설명을 입력란과 경쟁하도록 쌓지 않는다.
- WCAG 2.2 AA 명암 대비, iOS 최소 44포인트와 Android 최소 48dp 터치 영역을 충족한다.
- 상태를 색상만으로 표현하지 않는다.
- 더 큰 화면으로 확장하기 전에 390×844 iOS와 360×800 Android 배치를 검증한다.

색상표는 시험 전까지 가설이다. Light·Dark·Increased Contrast와 모든 상호작용 상태, 200% 텍스트, VoiceOver·TalkBack을 검증하고, 대표 사용자 5명 중 최소 4명이 3초 안에 입력을 다음 행동으로 식별하며 CTA를 일반 채팅이 아닌 첫 행동 생성으로 이해한 뒤 정확한 토큰을 확정한다.

## 4. 출시 범위

### 4.1 P0 — 양대 스토어 필수 범위

- 개인정보 정보, 인공지능 처리 설명, 의견·신고, 로컬 데이터 삭제 설정
- 전체 핵심 흐름의 iOS·Android 기능 동등성
- 접근성, 비정상 종료 없는 앱 수명 주기 처리, 스토어 설명 정보, 개인정보 공개, 베타 검증

### 4.2 명시적인 출시 이후 범위

- 대화형 코칭을 기본 진입 경로로 사용하는 기능
- 자유 입력 완료 인증 또는 서버 사진 업로드·동기화

## 5. 아키텍처 결정

### 5.1 결정

Expo 기반 React Native 모바일 앱을 만들고 현재 웹 앱의 플랫폼 중립 TypeScript 계약과 사업 로직을 재사용한다. 인공지능 인증정보가 클라이언트에 포함되지 않도록 Next.js 행동 계획 API를 서버 경계로 유지한다.

구현 계획의 확정 목표 구조:

```text
apps/mobile/             Expo 앱, 화면 이동, 네이티브 앱 수명 주기, 사용자 화면
packages/domain/         행동 계획, 타이머, 완료 인증, 경험치, 핵심 성과 지표 계약과 순수 로직
packages/events/         이벤트명, 스키마, 안정적인 식별자 도우미
app/api/coach/plan/      초기에는 유지하는 서버 행동 계획 경계
ios/StartioNative/       기능 동등성 참고 자료, 모바일 인수 기준 통과 뒤 과거 자료
```

기존 npm 패키지 관리자를 사용하고 현재 Next.js 앱을 유지하면서 루트 npm 작업공간에 `apps/mobile`을 추가한다. Expo Router를 사용한다. 테스트로 공용 경계를 증명한 뒤에만 `packages/*`를 추출한다. 이는 선행 대규모 단일 저장소 재구성을 허용하는 것이 아니다.

### 5.2 검토한 선택지

| 선택지 | 장점 | 비용·위험 | 결정 |
| --- | --- | --- | --- |
| SwiftUI·Kotlin 별도 클라이언트 | 네이티브 제어 최대화 | 개발, 테스트, 행동 분석, 앱 수명 주기 작업 중복 | 현재 팀 규모에서는 기각 |
| React Native + Expo | 하나의 제품 표면, 공용 TypeScript 로직, 관리형 iOS·Android 빌드 경로 | 네이티브 앱 수명 주기와 의존성 관리 규율은 여전히 필요 | 채택 |
| 웹 감싸기·Capacitor | 초기 재사용이 가장 빠름 | 네이티브 경험이 약하고 얇은 감싸기 앱은 스토어 심사 위험이 있음 | 핵심 상용 앱에는 기각 |

React Native는 새 앱에 Expo 같은 프레임워크 사용을 권장하며 Expo는 iOS·Android 빌드와 제출 흐름을 제공한다. [React Native](https://reactnative.dev/), [EAS Build](https://docs.expo.dev/build/introduction/), [EAS Submit](https://docs.expo.dev/submit/introduction/)을 참고한다.

## 6. 개인정보·안전·스토어 준비

원문 할 일은 행동 분석에서 제외하더라도 Startio 서버와 인공지능 제공자에게 전송된다. 최초 원격 요청 전에 사용자는 목적과 제공자 범주를 본 뒤 명시적이고 버전이 있는 선택을 해야 한다. 동의 전에 원문 할 일은 기기 밖으로 나가지 않는다. 거절하면 로컬 대체 계획을 사용하고 설정에서 선택을 철회·초기화할 수 있다.

로컬 행동 이벤트 기록은 기기 내 실행 기록과 핵심 성과 지표의 원천이다. 재계획 M25·M30이 `MORE(추가 결정 필요)`이므로 원격 행동 데이터 전송은 현재 비활성이다. 추후 명시적 결정으로 베타 전송을 승인하면 별도 버전별 참여 동의와 광고 식별자·이메일·기기 계정 식별자가 아닌 무작위 앱 범위 식별자를 사용해야 한다. 비활성 상태의 허용 목록은 앱·플랫폼·버전, 이벤트·시각, 안정적인 세션·할 일·행동 계획·단계 식별자, 단계 번호, 지속시간, 완료 상태, 대체 계획·오류 코드로 제한한다. 원문 할 일, 생성 행동·코치 문구, 사진·경로, 이메일, 진단·의료 데이터, 자유 입력 의견은 계속 금지한다. 승인된 구현도 전송 전에 제한된 대기열·재시도, 최대 90일 보관, 설치 식별자 삭제, 운영 통신 경로, 지정된 데이터·삭제 담당자를 확정해야 한다.

선택적 인증 사진은 앱 소유 로컬 저장소에만 보관하고 사용자가 첨부를 선택할 때만 요청하며 실행 기록에 로컬 미리보기로만 표시한다. Startio 서버, 원격 행동 데이터, 콘텐츠 신고로 보내지 않고 경로도 이벤트 필드가 아니다. 전체 로컬 삭제는 원본·미리보기·인증 기록을 함께 지운다. 선택한 Expo 기준선은 출시 전에 파일 수명 주기와 운영체제 백업 동작을 검증해야 한다.

콘텐츠 신고는 별도의 명시적 제출을 사용한다. 사용자는 신고할 생성 출력을 미리 확인하며 직접 추가하지 않는 한 원문 할 일은 제외한다. 베타 전에 신고 통신 경로의 수신 확인, 재시도·멱등성, 보관, 접근 통제, 고객지원 담당자를 확정해야 한다.

필수 통과 기준:

- 인공지능 키를 서버에 보관하고 공개 행동 계획 통신 경로에 요청 크기, 악용·빈도 제한, 응답 제한시간, 관측 정보를 추가한다.
- 운영 원격 행동 데이터 담당자와 URL을 확인한 뒤에만 별도 허용 목록 이벤트·삭제 경계를 추가한다. 콘텐츠 신고를 분리하고 자유 입력 행동 계획 전송 내용을 어느 쪽에도 재사용하지 않는다.
- 원문 할 일, 의료 추론, 개인정보를 행동 분석에 넣지 않는다.
- [Google Play 인공지능 생성 콘텐츠 정책](https://support.google.com/googleplay/android-developer/answer/13985936)에 맞춰 공격적이거나 안전하지 않은 생성 콘텐츠를 앱 안에서 신고할 수 있게 한다.
- 홍보 가정이 아닌 실제 데이터 흐름을 기준으로 [Apple 앱 개인정보](https://developer.apple.com/app-store/app-privacy-details/)와 [Google Play 데이터 안전](https://support.google.com/googleplay/android-developer/answer/10787469)을 작성한다.
- iOS 의존성에 필요한 개인정보 명세를 포함하고 제3자 소프트웨어 개발 도구 선언을 검증한다. [Apple 개인정보 명세](https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk)를 참고한다.
- 이후 계정을 추가하면 제출 전에 앱과 웹에서 계정을 삭제할 수 있게 한다. [Apple 계정 삭제](https://developer.apple.com/support/offering-account-deletion-in-your-app/)와 [Google Play 계정 삭제](https://support.google.com/googleplay/android-developer/answer/13327111)를 참고한다.
- 현재 제출 요건에 맞춰 빌드한다. Apple은 2026년 4월 28일부터 iOS 26 SDK 이상을 요구하고 Google Play는 현재 목표 API 준수를 요구한다. 출시일에 [Apple 제출 요건](https://developer.apple.com/app-store/submitting/)과 [Google 목표 API 요건](https://developer.android.com/google/play/requirements/target-sdk)을 다시 확인한다.

## 7. 개발 일정

이 일정은 제품·디자인 담당자 한 명과 여러 직무를 담당하는 개발자 두 명의 소규모 팀을 가정한다. 날짜는 약속이 아닌 작업 목표다. 팀 인력, 개발자 계정 생성 시점, 심사 의견을 스프린트 0에서 확인해야 한다.

제작 순서는 화면 단위 iOS-first다. 각 화면은 390×844 iOS에서 위계·입력·키보드·Dynamic Type·VoiceOver를 먼저 교정하고, 같은 Expo 수직 기능 안에서 360×800 Android의 48dp·TalkBack·edge-to-edge·키보드 동등성을 통과해야 다음 화면으로 진행한다. 전체 iOS 앱을 먼저 완성하거나 iOS 우선 출시하는 방식은 아니다.

| 스프린트 | 목표 | 종료 증거 |
| --- | --- | --- |
| 0 | 제품 기준·아키텍처 확정 | 승인된 제품 요구사항·시험 명세, 개발자 계정 확인, 저장소·원격 행동 데이터·신고 결정, 개인정보 흐름 지도, 시제품 계획 |
| 1 | 직접 입력 디자인 검증 | 390×844 iOS 시제품 교정 뒤 360×800 Android 동등성 통과, 사용자 5명 시험, 수정된 시각 토큰, 스크롤 없는 첫 행동 |

## 8. 인수·학습 통과 기준

### 8.1 제품 인수 기준

- 390×844 iOS와 360×800 Android에서 입력란과 핵심 실행 버튼을 스크롤 없이 사용할 수 있다.
- 유효한 할 일 입력 뒤 필수 추가 질문은 0개다.
- 입력 제출 한 번과 최대 두 번의 누르기로 타이머에 도달한다.
- 성공한 행동 계획은 정확히 세 개의 행동과 관찰 가능한 1단계를 포함한다.
- 1·2·3단계가 순서대로 실행되고 재실행 시 완료를 잘못 지급하지 않은 채 현재 단계를 복구한다.
- 원격 요청 제한시간은 M21 해소 전까지 제품 확정값이 아니다. 시험용 임시값 8초를 주입해 검증하고, 제한시간을 넘긴 요청은 중단한 뒤 계약에 맞는 로컬 대체 계획을 보여준다.
- 안전한 할 일의 대체 계획은 정확히 세 개의 행동, 행동·완료 조건 문구, 단계별 안정적인 식별자, 15~20초의 1단계 타이머를 포함하며 한 번 누르기로 타이머에 도달한다.
- 핵심 흐름의 화면마다 시각적으로 가장 강한 동작을 하나만 보여준다.
- 핵심 동작의 방향은 따뜻하고 차분한 파스텔 오렌지로 인식되고 코발트가 브랜드·핵심 동작을 지배하지 않는다.
- 원색 오렌지, 단일 오렌지 위계, 넓은 오렌지 배경·그라디언트, 레거시 오렌지 카드·대시보드를 사용하지 않는다.
- 지원하는 iOS·Android 기기 시험 행렬에서 전체 P0 흐름이 같은 의미로 동작한다.
- 체크만으로 완료할 수 있고 선택적 사진은 로컬에만 남으며 사용자가 선택한 경우에만 실행 기록 미리보기로 표시되고 전체 삭제 시 제거된다.
- 원격 투영 테스트에서 원문 할 일, 생성 문구, 사진·경로, 이메일, 의료·진단, 자유 입력 필드가 0건이다.

### 8.2 성능 목표

- 최소 지원 시험 기기에서 할 일 입력란을 1.5초 안에 조작할 수 있다.
- 행동 계획 응답시간 목표는 중앙값 3초 이하다. 95백분위와 제한시간 8초는 M21 해소 전 임시 측정값이며 제품 확정값이 아니다. 대체 계획 시간은 따로 측정한다.
- 모든 모의 응답 제한시간 초과와 인공지능 제공자 실패에서 대체 계획으로 계속 진행한다.

### 8.3 베타 판단 지표

새 경로를 현재 대화 우선 iOS 시제품과 비교한다.

- 앱 실행부터 타이머 시작까지의 중앙값이 최소 40% 감소한다.
- 5분 안의 할 일 제출 → 타이머 시작 전환율이 최소 15%포인트 개선된다. 이 비율은 유효한 고유 제출 중 5분 안에 첫 `timer_started`가 이어진 수를 모든 유효한 고유 제출 수로 나눈다. 해당되는 대체 계획 세션은 분자와 분모에 모두 포함한다.
- 행동 계획 수락 전 이탈이 최소 30% 감소한다.
- 대표 베타 참여자 최소 20명 중 90% 이상이 진행자의 도움 없이 타이머를 시작한다.

이는 제품 판단 기준이지 건강·치료 주장이 아니다.

기준을 충족하지 못하면 사용자 경험을 다시 수정하고 측정한다. 출시는 기준 통과 또는 증거 공백·담당자·후속 확인일을 기록한 명시적 제품 위험 예외 승인이 있어야 한다. 대화 우선 기준선을 신뢰할 수 없으면 개선율을 주장하지 않고 시험 명세의 진행자 동반 비교 연구를 사용한다.

## 10. 스프린트 0에서 해소할 가정

- Apple·Google 개발자 계정 소유권, 법적 주체, 계정 생성 시점을 확인한다.
- 최소 지원 운영체제 버전과 실기기 시험 행렬을 확인한다.
- Expo·React Native 기준선, 개발 빌드 흐름, 묶음·패키지 식별자, EAS 인증정보 담당자, 지속적 통합 서명 담당자, 의존성 개인정보 목록을 확인한다. Expo Go는 출시용 개발 환경이 아니다.
- 외부 사용자가 이전해야 할 SwiftUI 로컬 데이터를 보유했는지 확인한다.
- 팀 인력, 출시 예산, 고객지원 연락처·응답시간, 개인정보·데이터 담당자, 로컬 운영체제 백업 동작, 인공지능 제공자 보관 설정을 확인한다.
- 제품 담당자가 `release_window_sla`에 서명한다. 작업 목표는 같은 달력 날짜 안, 최대 허용시간 48시간이며 이를 지키지 못할 때의 조치도 포함한다.

해소 전에는 계정 없음, 결제 없음, 과거 사용자 데이터 이전 없음, 같은 분이 아닌 공동 공개를 가정한다. `release_window_sla` 서명 전까지 운영 공개는 차단한다.
